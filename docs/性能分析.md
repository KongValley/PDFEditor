## 0 结论摘要

三条主线,按"收益÷风险"排序:

| # | 项 | 现状 | 可省 / 收益 | 风险 |
|---|---|---|---|---|
| 1 | 安装包死重量 | `app.asar` = **65.5 MB**,其中 `node_modules` **55.9 MB(85%)**;而 `out/main/index.js` 只 `require("electron")` + node 内置模块(0 个外部包),渲染层资源也全部打进 `out/renderer` 【实测+代码】 | **55.9 MB(85%)**;改 `package.json` 依赖归类 + 一次打包实测 | 低,但需在 README 说明"依赖已全部打包"的约定 |

## 2 逐项分析

### P0-1 asar 的 85% 是运行时用不到的死重量【实测】

**现象**:`app.asar` 65.5 MB,其中 `node_modules` 55.9 MB。但运行时不加载其中任何一个包:

1. 主进程 bundle 自包含 —— `out/main/index.js` 的外部 `require` 只有 `electron` 与 node 内置模块,`fontkit` 出现 21 次、`pdf-lib` 只作为字符串出现 3 次(即已被 vite 内联),bundle 内 `node_modules` 字符串 0 处【实测 grep】;
2. 渲染层 bundle 自包含 —— `out/renderer/assets/` 里已有 `index-*.js` 与 `pdf.worker.min-*.js`(worker 经 `?url` 被 vite 复制);`cmaps/`、`standard_fonts/` 由 `scripts/sync-pdfjs-assets.mjs` 在构建期从 `node_modules/pdfjs-dist` 复制进 `src/renderer/public` → 打包进 `out/renderer`【代码:脚本 + `out/renderer/` 实际内容】;
3. 生产依赖闭包被 electron-builder 整包拷进 asar —— 拷贝逻辑由 `package.json` 的生产依赖驱动,与"是否真的被 require"无关【代码】。

**改法**:
1. `package.json`:把 `pdfjs-dist`、`pdf-lib`、`@pdf-lib/fontkit` 全部移入 `devDependencies`(三者只在构建期被 vite 与 `scripts/sync-pdfjs-assets.mjs` 消费);
2. 不要指望用 `build.files` 的 `!node_modules` 排除 —— electron-builder 的 node_modules 拷贝是独立通路,复用主 matcher 的 patterns 且以生产依赖闭包为输入【代码:app-builder-lib 的 `appFileCopier.js`/`NodeModuleCopyHelper.js`】,移动依赖归类才可靠;
3. 在 README「构建/打包」一节补一句约定:所有依赖均由 electron-vite 打进 `out/`,因此都放 `devDependencies`;若将来改用 `externalizeDepsPlugin`,必须同时把对应包移回 `dependencies`。

**预期**:asar 65.5 → ≈6.0 MB(仅剩 `out/`),安装包/便携版同步缩小,启动解压与磁盘占用下降。
**验证**:`npm run dist` 后重新解析 asar 头核对 <10 MB;`npm run smoke` 全绿。

### P0-2 页面与缩略图全量挂载(无虚拟化)【代码】

**现象**:两个面板都按页数一次性创建组件,且**永不卸载**:

- `src/renderer/src/viewer/PdfViewer.vue:246-264` —— `v-for="(pages,row) in spreadRows"` + `v-for="n in docState.pageCount"`(单页模式用 `v-show`,DOM 仍在);
- `src/renderer/src/components/ThumbnailsPanel.vue:205` —— `v-for="item in items"`,每项一个 `PageThumb` canvas + checkbox + label。

每个 `PageCanvas` 的模板是**全尺寸**包裹 div(`:style="{ width: size.w + 'px', height: size.h + 'px' }"`,`size` 来自 `pageDisplaySize()`)+ 绝对定位的 canvas + 空的 `.textLayer` div + 一个 `.search-layer` svg;`setupObserver()` 对**每一页**都 `observer.observe`(`PdfViewer.vue:105-128`,缩略图同理 `ThumbnailsPanel.vue:52-75`)。1000 页文档 = 1000 个全尺寸 div + 1000 个 canvas 元素 + 约 3000 个附加节点参与样式计算与响应式追踪(未渲染的 canvas 尺寸为 0,不贡献布局 box,但仍在 DOM 树里)。

**改法**:
1. **廉价版**:`.page-wrap` / `.thumb-box` 加 `content-visibility: auto`,并用内联 `contain-intrinsic-size: <w>px <h>px` 给**与实际渲染尺寸相同**的值(与 `pageDisplaySize()` 同源)。Electron 22 = Chromium 108,`content-visibility` 与双值 `contain-intrinsic-size` 都支持【代码:electron.vite.config.ts 注释 + Chromium 版本对应】。它省的是离屏页的布局/绘制与样式计算,**DOM 节点数不变**。
2. **彻底版**:只挂载可见窗口 ±1 屏,复用已有滚动几何(`viewer.ts` 的 `pageOffsetTop`/`contentHeight`)。

第 1 条的唯一风险:`contain-intrinsic-size` 与真实高度不一致会让 `scrollToPage(page)` 落偏 —— 两者必须同源。若页数极大(≥1000)仍需第 2 条。
**验证**:`scripts/smoke/step16-view.js`(滚动/视图)、`step6.js`(大文档)、`step10-mem.js`(内存)。

### P1-1 拆分时逐块重读 9.75 MB 中文字体【实测+代码】

**现象**:`src/main/lib/docops.ts:207-234` 在每个输出块的循环内调 `createAnnotContext`(`:219`)→ `loadCjkFontBytes()` 每次 `readFileSync('C:/Windows/Fonts/simhei.ttf')`(**9.75 MB**【实测】)+ `doc.embedFont(bytes, {subset:true})` 重新 `fontkit.create()` 解析【代码:`pdflibwrite.ts:70-94`】。按"每 1 页一个文件"拆 100 页 = **≈975 MB 磁盘读** + 100 次字体解析;且判定条件只看"有没有批注"(`:217`),**不看批注类型** —— 只有图形批注的文档也照样嵌入整份字体。

导出路径同样是"每文档一次"(`docops.ts:98-103`);保存路径是**无条件**的(`pdflibwrite.ts:649-652`,`writeAnnotations` 里直接建 ctx,即使零批注零表单)。

**改法**:
1. `pdflibwrite.ts` 内做模块级字体字节缓存(`loadCjkFontBytes` 只读一次盘);
2. 仅当该输出文档含 `text`/`note`/`stamp`/`measure` 批注时才嵌入字体(现在是无条件)。

注:`embedFont` 是按文档注册的,**不能跨文档复用字体对象**,能省的只有"读盘 + 解析"与"无文本时的整体跳过"。
**验证**:`scripts/smoke/step13-batch.js`(批量拆分/合并)。

### P1-2 页面操作后整份重建文档状态【代码】

**现象**:任何页面操作后 `reloadDocument()`(`src/renderer/src/store/document.ts:250-262`)无条件做两件 O(页数)的事:

1. `fillPageBoxes()` —— 每页一次 `getPage`(`document.ts:159-180`,32 个一批并发);
2. `discoverFormFields()` —— 每页一次 `getPage` + `page.getAnnotations()`(`lib/forms.ts` 全页循环)。

(`loadOutline` 只在 `openByPath` 里调用一次,`document.ts:238` —— 不在本项范围内。)
对 500 页文档,一次"旋转一页"要付 ≈1000 次 `getPage` 往返 + 500 次 `getAnnotations`。

**改法**:用 `PageOp` 已返回的 `pageMap` 增量维护,避免全量 `getPage`:

| 操作 | pageBoxes | 表单字段 |
|---|---|---|
| `delete` / `move` | 按 `pageMap` 重排(纯数组操作,0 次 `getPage`) | `field.page` 用同一 `pageMap` 迁移(`applyPageMap` 已是同构逻辑) |
| `insertBlank` | splice 一个已知尺寸的 box | 迁移 + 仅新页若有 Widget 才重新发现 |
| `append` | 只为新增页补 box(尺寸可在主进程 pdf-lib 侧顺带返回) | 需要发现新增页的字段 |
| `rotate` | 只重算被旋转页的 w/h 对调 | 页序不变,可不重建 |

注意:`delete`/`insertBlank`/`move` 都会改变页序,**不能**整体跳过表单字段维护,只能改成"用 pageMap 迁移 + 按需发现";只有 `rotate` 可以完全跳过。`openByPath` 首次仍需要一次全量 `fillPageBoxes`(没有旧数据可迁移),这可以接受。
**验证**:`step12-pages-range.js`、`step13-batch.js`、`step6.js`。

### P1-3 打开流程:一次读盘 + 两次全量解析 + 两次整份拷贝 + 2N 次 getPage【代码】

**现象**:一次"打开"的顺序 ——
1. 主进程 `readFile` + `PDFDocument.load`(pdf-lib 全量解析,`pdfio.ts:130-167`)+ `extractEditorAnnotations`(`:148`,遍历所有页 `/Annots`);
2. `toArrayBuffer(buffer)` 复制一份(`pdfio.ts:75-77`)→ **整份文件字节走 IPC 结构化克隆**给渲染层;
3. 渲染层 `pdf.js getDocument`(再解析一遍);
4. 渲染层 `fillPageBoxes`(N × `getPage`)+ `discoverFormFields`(N × `getPage` + N × `getAnnotations`)+ `loadOutline`(`document.ts:225/229/238`)。

200 MB 文档 = 1 次读盘 + 2 次全量解析 + 2 次整份拷贝(内存 + 跨进程)+ 2N 次 `getPage`。
另:`doc:getAnnotations`(`ipc.ts:82-88`)在合并后会**再解析整份 PDF**。

**改法(改动大,建议单独排期)**:
- 无编辑态时让 pdf.js 直接按路径流式加载(`app://` 协议加 Range 支持),省掉整份 buffer 过 IPC;
- `openDocument` 已经是单次 `PDFDocument.load`,但 `doc:getAnnotations` 可以复用同一份解析结果(或直接从内存 buffer 里按页扫 `/Annots`,免全量解析)。
**验证**:`step6.js`(大文档)+ `test-api.ts` 已有的 `openPathReady` 计时日志。

### P1-4 每次保存:字体读盘 + 逐条批注建临时页【代码】

**现象**:`writeAnnotations`(`pdflibwrite.ts:649-656`)每次保存都:读 9.75 MB 字体 + `fontkit.create` → `replaceOwnAnnotations` 对**每条**批注 `buildAppearance`(`:336-345`:`doc.addPage(scratch)` → 画 → `embedPage` → `removePage`)→ `doc.save()`。500 条批注 = 500 次加页/嵌页/删页 + 500 个 Form XObject。

**改法**:
- 字体字节走模块级缓存(见 P1-1),无文本批注时跳过嵌入;
- `buildAppearance` 复用**同一个 scratch 页**:一次保存内只 `addPage` 一次,每条画完 `embedPage` 后重置内容流,最后统一 `removePage`,把 500 次页操作降到 1 次。

风险:scratch 页复用需要显式重置内容流(`page.node.set(PDFName.of('Contents'), …)`),否则外观互相叠加 —— 改动集中在 `buildAppearance`,可冒烟验证。
**验证**:`step15-annots.js`(分类批注往返 + 像素比对)、`step1.js`/`step8.js`(便签/墨迹基线像素)。

### P1-5 缩放无去抖,连续 Ctrl+滚轮反复取消渲染【代码】

**现象**:`PdfViewer.vue:84-103` 的 `handleWheel` 每个 wheel 事件直接 `zoomAt(scale × 1.1)`(Ctrl/⌘+滚轮分支在 `:85-89`)→ `docState.scale` 同步变更 → 每个可见 `PageCanvas` 的 watch(`PageCanvas.vue:261-268`)立即 `renderPage()`,而 `renderPage` 在开始渲染前 `renderTask?.cancel()`。连续滚 10 格 = 10 轮"全可见页渲染启动 → 被下一轮取消"。渲染层其余地方没有缩放去抖(仅搜索栏有 300 ms 去抖,`SearchBar.vue:45-46`)【实测 grep】。

**改法**:在 `PageCanvas` 的 scale 变更路径上做 100–150 ms 去抖(或合并到一次 `requestAnimationFrame`),拖动期间由 CSS `transform: scale()` 占位;一次性变更(`fitWidth`/`fitPage`/菜单选比例)可立即渲染。
**验证**:`step16-view.js`。

### P2-1 拖拽批注无节流,每个 pointermove 全量重算各层过滤【代码+实测】

**现象**:`AnnotationLayer.vue:325-366` 的 `onDragMove` 在每个 `pointermove` 上直接 `patchAnnotation`;`patchAnnotation`(`store/annotations.ts:190-194`)是**整项替换** + `normalize()`,而 `normalize`(`:140-145`)对 `ink`/`arrow`/`measure` 会重算 `annotationBounds` → `pointsBounds` 是 O(点数)(`shared/types.ts:130-152`)。多选移动时每个事件对每个被拖批注各写一次(`AnnotationLayer.vue:336-338`)。

**Vue 响应式代价(实测,见 §5 实验)**:对 `items[i]` 的单次 index 写入会让**所有** `AnnotationLayer` 的 `items` computed 重算(每层一次全量 `filter`,=`挂载层数 × 总批注数`)+ `AnnotationsList` 的 `pageItems` 重算;**未变动的批注形状不会重渲染**(props 引用未变,Vue 跳过子组件更新)。

**改法**:`pointermove` 只更新局部变量,用 `requestAnimationFrame` 每帧提交一次 `patchAnnotation`;多选移动期间只动 DOM(transform),`pointerup` 一次性提交。
**验证**:`step15-annots.js` 的拖拽/缩放场景。

### P2-2 滚动与缩放几何都是 O(页数)【代码】

**现象**:`store/viewer.ts` —— `contentHeight`(`:41-51`,循环在 `:44`/`:46`)、`pageOffsetTop`(`:53-62`,循环在 `:57`/`:60`)、`computeCurrentPage`(`:91-108`,循环在 `:97`/`:103`)全部用**累加循环**;`computeCurrentPage` 被 `PdfViewer` 的滚动处理每帧调用一次(`PdfViewer.vue:74-82`,已 rAF 节流)。

**改法**:在 `pageBoxes` / `scale` / `rotationView` / `viewMode` 变化时重建一次**前缀和数组**(`offsets[i]` = 第 i 页顶部 y),查询改为二分。1000 页文档把每帧 O(N) 降为 O(log N);`rowHeight`/`rowPages` 的重复 `pageDisplaySize` 调用可一并缓存。
**验证**:`step16-view.js`。

### P2-3 每页全量过滤(批注 + 搜索命中)【代码】

- `AnnotationLayer.vue:32` —— 每层对 `annotState.items` 做一次全量 `filter`;批注越多、挂载层越多,单次变更的总比较量越大(见 P2-1 实验)。
- `PageCanvas.vue:31-43` —— `searchRects` 遍历**全部** `searchState.results`;改 `searchState.current`(F3 / 下一条)会让**所有已渲染页**(`viewport` 非空的页;`:33` 对未渲染页提前返回)重算一遍,复杂度 O(已渲染页 × 命中数)。

**改法**:两处都改成"按页分桶"的 `computed`(`Map<pageIndex, T[]>`,在 `annotState.items` / `searchState.results` 变化时重建一次),每页只做一次 Map 取值。
**验证**:`step15-annots.js`(批注)、`step5*`/`step14-ux.js`(搜索)。

### P2-4 `visiblePages` 用 reactive Set 驱动全量模板求值【代码+实测】

`PdfViewer.vue:19` 是 `reactive(new Set<number>())`,模板里 `:visible="visiblePages.has(n)"` 对**每一页**求值(`:252`/`:262`)。IntersectionObserver 每批投递都会让整个 viewer 的 render effect 重跑一次,其中包含 N 次 `has()` 调用(实测:1000 页场景下 `add(1)` → effect 重跑 1 次、`has()` 调用 1000 次,见 §5)。
**改法**:P0-2 的窗口化会让这一项自然消失;若暂不做,可换成 `shallowRef` + 显式版本号,只让几何计算定序。

### P3-1 长图导出把整份文档留在内存【代码】

`lib/actions.ts` 的 `exportPagesAsImages(mode:'long')` 先把**所有页**渲染成 `HTMLCanvasElement[]` 累积在内存,再建一张总尺寸 canvas 逐张 `drawImage`。100 页 A4@2x ≈ 100 × 8.0 MB(1190×1684×4B)= 800 MB,总图同量级【实测算术】。

**改法**:先按页尺寸算总高/总宽,直接画进目标 canvas(省掉中间 100 张);并设页数上限 + 明确提示。另外 Chromium 对单个 canvas 有面积上限(≈2.68 亿 px,即 ≈128 页 A4@2x 的纵向长图)【推断,未实测】,触及后是"直接失败"而不是"变慢"。
**验证**:`step12-pages-range.js` 的 PNG 导出分支 + 大页数手测。

### P3-2 打印逐页 PNG + base64 过 IPC【代码】

`lib/actions.ts:renderPrintPageDataUrl` 用 `canvas.toDataURL('image/png')`(PNG 编码最慢),300 dpi A4 = 2480×3508 px(≈34.8 MB 位图)后编码,再把 base64 字符串(体积 ×1.33)经 `app:printAddPage` 发给主进程落盘。
**改法**:改用 `image/jpeg`(质量 0.9–0.95)或 `toBlob` + `ArrayBuffer`(`ipcRenderer.invoke` 支持结构化克隆,不必 base64)。
**验证**:`step18-print.js`(含清晰度像素校验)。

### P3-3 搜索索引无上限 + 每次搜索重复小写化【代码】

`lib/textsearch.ts:23` 的 `indexCache` 无容量上限(每页一份拼接文本,只保存被搜索过的页);`searchDocument` 每次对整页文本重新 `toLowerCase()`(`:99`),且 `matchRects` 对每条命中线性扫 `items`(`:54` 起)。

**核验说明**:索引**会**随文档切换清空 —— `components/SearchBar.vue:79-88` 监听 `docState.docId`,清空索引、结果、当前项与查询词;页面操作/撤销走 `invalidateSearch()`【代码】。原稿曾把"换文档不清索引"列为正确性问题,**核验后证伪**(详见 §5)。
**改法**:给 `indexCache` 加上限(与 `PAGE_CACHE_LIMIT` 同思路);索引项同时缓存 `textLower`;`matchRects` 可对 items 建行桶。

### P3-4 每次导出/保存都 JSON 深拷贝全部批注【代码】

`store/annotations.ts:570-572` 的 `exportAnnotations()` 是 `JSON.parse(JSON.stringify(items))`,被页面操作(记录撤销现场)、导出、拆分、合并、保存反复调用;批注含墨迹点数组时是 MB 级深拷贝。
**改法**:只在跨 IPC / 入历史时克隆,页面操作里"记录现场"可与"发送给主进程"复用同一份克隆。

---

### P3-5 读页数为拿页数整份解析【代码】

`pdfio.ts:112-128` 的 `readPdfPageCount` 为每个文件做一次完整 `PDFDocument.load`;`ipc.ts:97` 是 `Promise.all`,峰值同时驻留多份解析结果【推断:内存峰值 = 文件数 × 文件大小量级】。
**改法**:改顺序执行以降内存峰值;或对未加密文件用"读 trailer/页对象树"的快速路径,失败再回退全量解析。

### P3-6 文本批注每个实例一个 2D context【代码】

`AnnotationShape.vue:15` 每个组件实例各建一个 `canvas.getContext('2d')` 用于 `measureText`;`canvasannot.ts` 已是模块级共享。
**改法**:抽到模块级共享(与 `canvasannot.ts` 同构)。

### 5.2 Vue 响应式粒度实验(离线,用仓库内 `node_modules/vue`)

复现方式(不依赖应用):构造 `reactive({items:[1000 条]})`,对 5 个"页"各建一个 `computed(() => items.filter(...))` 并 effect 订阅,然后执行一次 `items[3] = {...items[3]}`(即 `patchAnnotation` 的写法):

| 观测 | 结果 | 对应结论 |
|---|---|---|
| 各层 filter computed 重算次数 | 5 / 5(全部重算) | P2-1:单次写入 → 每层一次全量 `filter` |
| 未变动批注的 `computed` 重算次数 | 0 | P2-1:形状不会因他人变更而重渲染(原稿此处说错) |
| `reactive(new Set())` 中 `add(1)` → 订阅该 Set 的 render effect 重跑次数 / 其中 `has()` 调用次数 | 1 次 / **1000 次** | P2-4:全量求值属实 |
