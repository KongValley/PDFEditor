## P0 — 数据丢失/安全问题(优先修)

### P0-0 并发打开无请求身份守卫 → 跨文档状态损坏,最坏可把 A 的批注写进 B 的 PDF(store 层)
- **位置**:`src/renderer/src/store/document.ts:257-356`(`openByPath`)、`src/renderer/src/lib/actions.ts:89-107`(`openPath`)
- **已核实**:①`openByPath` 全程**没有任何请求身份令牌**(无 seq/generation 守卫),却在多处 `await` 之后直接写全局 `docState`;
  ②`openPath` / `openFileDialog` / 拖放(`App.vue:88`)/ 最近列表(`App.vue:126`)/ 工具栏「打开」(`Toolbar.vue:33`,无 `:disabled`)
  **都没有 `docState.loading` 守卫**,而 `Ctrl+O`(`keymap.ts:31-34`)被**故意放在输入守卫之前** → 并发打开完全可达。
- **触发**:打开一个还在 `fillPageBoxes`(:330,大文档要数秒)时,再按一次 `Ctrl+O` 或再拖入一个文件。
- **后果链**:A 尚在 `await fillPageBoxes` 时 B 已完成并设 `pdfDoc=B`;随后 A 恢复执行 →
  ①`:316 destroyPdfDocument(docState.pdfDoc)` **销毁 B 正在用的 doc**;②`:333 docState.pageBoxes = boxesA` → **B 的 pdfDoc 配 A 的页面几何**,
  批注按错误尺寸绘制;③A 返回 `true` → `openPath` 继续 `restoreSidecar()` → `resetAnnotations(A 的批注)` →
  此时模型里是 **A 的批注、pdfDoc 是 B** → 用户按 `Ctrl+S` 即**把 A 的批注写进 B 的 PDF**(数据损坏);
  ④`finally`(:351-354)先返回者会把 `loading=false`,掩盖另一路仍在进行。
- **修复**:引入单调递增的 `openSeq`,`openByPath` 开头捕获、每个 `await` 之后校验 `seq === openSeq`,不匹配则丢弃并释放已申请的主进程条目;
  并在 `openPath` 入口加 `if (docState.loading) return`(或让第二次打开排队)。

### P0-1 加密文档「另存为」静默摧毁目标路径旁既有 sidecar,且不生成 PDF
- **位置**:`src/main/ipc.ts:414-423`(加密分支) + `src/renderer/src/lib/actions.ts:131-161`
- **已核实**:加密分支只写 sidecar、**完全不写 PDF**,却 `return { ok:true, mode:'sidecar', savedPath: targetPath }`;
  渲染层据此执行 `docState.filePath = result.savedPath`(`actions.ts:154`)并清脏标记(`:156`)。
- **触发**:打开**加密** PDF → 加批注 → 另存为 → 目标选到一个**已存在** PDF 旁(该 PDF 有自己的 `.pdfanno.json`)。
  `saveDocumentAs → saveTo(undefined)`(`actions.ts:121`)不做加密判断,`writeSidecar` 默认 true。
- **后果**:①目标路径旁的**他人/自己** sidecar 被整体覆盖,原文档标注静默丢失;②用户以为新 PDF 已生成,
  实际只有一个孤立 sidecar——删掉它即全丢;③`filePath` 指向不存在的 PDF。
- **修复**:落盘前校验 `targetPath` 已存在且 ≠ `entry.path` → 拒绝或显式二次确认「将覆盖其 sidecar」;
  另存为到新路径时,加密分支不要把 `filePath` 指向未生成的 PDF。

### P0-2 不可信 PDF 的 `/PdEditorData.refPath` 可让主进程读任意本地文件并嵌入产物
- **位置**:解析端 `src/main/lib/pdflibwrite.ts:716-739`;使用端 `src/main/ipc.ts:428,577-579`、`src/main/lib/images.ts:48,104-118`;渲染层 `src/renderer/src/lib/actions.ts:76`、`src/renderer/src/store/annotations.ts:368`
- **已核实攻击链**:打开他人 PDF → `/PdEditorData`(kind:'image')的 `refPath` 指本机任意绝对路径 →
  打开时 `img:getByPath → readImageInfo → readFile(refPath)`(`images.ts:48`)读盘回传 dataUrl;
  保存时 `resolveImage → readImageBuffer(refPath)`(`ipc.ts:428`)再读一次并**嵌入用户导出的 PDF**。
  `extractEditorAnnotations` 仅校验 `id`/`kind` 是字符串(`:732`),`refPath` 未做任何白名单。
- **缓解**:魔数校验(`images.ts:36-40`)只放行 PNG/JPEG 文件头;但任何头部像 PNG/JPEG 的文件都会被读+嵌入。
- **修复**:解析结果做结构化校验(`kind` 白名单、数值 `Number.isFinite`、字符串长度上限);
  `refPath` 只接受「用户经 `img:choose` 实际导入过的路径集合」——**落盘 PDF 里的路径不应成为读盘授权凭据**。

## P1 — 功能缺陷(本轮修)

### P1-0 拖拽中页面被移出可见集 → `ui.dragging` 永久为 true,Ctrl+S / Ctrl+Z 整个会话失效(视图层,最隐蔽)
- **位置**:`src/renderer/src/viewer/AnnotationLayer.vue:566-575`(`onBeforeUnmount`)、置位点 `:285`/`:313`;消费点 `src/renderer/src/lib/keymap.ts:38` 与 `:117`
- **已核实**:`onBeforeUnmount` 移除了全部 window 监听器,但**没有复位 `ui.dragging`**;而 `keymap.ts` 的
  `Ctrl+S`/`Ctrl+Z` 都以 `if (ui.dragging) return` 短路。`onDragEnd()` 里有复位,但卸载路径绕开了它。
  `AnnotationLayer` 是 `v-if="viewport"`,`clearPage()` 会把 viewport 置 null → 卸载可达。
- **触发**:按住注释拖动的同时该页离开可见集。①拖动中滚动使页面滑出 rootMargin;
  ②`refreshVisiblePages()` 先 `next.clear()`,任何 `prefetchEpoch` 变化/视图模式切换都会让 PageCanvas 走 `clearPage()`。慢机上②极易撞上。
- **后果**:①最后一帧位移被静默丢弃,注释弹回原位;②`ui.dragging` 永远为 true,**Ctrl+S 和 Ctrl+Z 从此毫无反应** ——
  用户按了没反应会以为已保存,必须重启应用。
- **修复**:`onBeforeUnmount` 末尾补 `ui.dragging = false`,并把拖拽位移提交或回滚后再清 `drag.value`。

### P1-1 单页模式下切到非首页时 `setupObserver` 进入永不退出的 rAF 自旋(视图层,常驻 CPU)
- **位置**:`src/renderer/src/viewer/PdfViewer.vue:126-135`(`setupObserver`)、模板 `:320-326`、触发入口 `:273-285`
- **已核实**:`root.querySelector('[data-page]')` 永远取**第一个**匹配元素(第 1 页)。单页模式用 `v-show`
  而非 `v-if`(`:321`),非当前页只是 `display:none` → 第 1 页 `getBoundingClientRect().height` 恒为 0 →
  每帧无条件重排 rAF,**且此路径没有任何重试上限**(同文件 `seedVisiblePages` 有 `seedRetries < 5`,说明作者知道这个坑,唯独漏了这里)。
- **触发**:当前页 ≠ 1 时切单页模式(`Ctrl+2`);或单页模式翻几页后渲染均值跨过 400ms 阈值翻转 `prefetchEpoch`(同一路径)。
- **后果**:①永久 60fps rAF 自旋,每帧一次 `querySelector` + 强制同步布局,在 Win7 32 位上是可感知的常驻 CPU 占用;
  ②`observer?.disconnect()`(:127)已执行但新 observer 永远建不起来,**预读缓冲彻底失效**。
- **修复**:rAF 重试加上限;并改为探测「任一可见页面」而非首个元素(`find(el => getComputedStyle(el).display !== 'none')`)。

### P1-4 「恢复上次阅读位置」对打开耗时 > 700ms 的文档**永久失效**(store 层,已上线功能静默失效)
- **位置**:`src/renderer/src/store/reading.ts:43-52`(`scheduleSettle`)、`:68-82`(watcher);`src/renderer/src/store/document.ts:312-333`;`src/renderer/src/lib/actions.ts:105-106`
- **已核实(时序逐步核对)**:
  1. `document.ts:312` 置 `docId` → docId watcher(`reading.ts:69`)触发 → `scheduleSettle()` 捕获 `path=新路径`、`page=1`(同帧内 `:313`/`:323` 已同步赋值),**起 700ms 定时器**;
  2. 紧接着 `:330 await fillPageBoxes(...)` —— 大文档(数百页)要**数秒**;
  3. 700ms 到点时定时器**无条件**执行 `:50` `app:recentSet({path: 新路径, page: 1})`
     (注意它**在身份守卫 `:49` 之外**,守卫只保护 `pushEntry`,不保护落盘);
  4. `openByPath` 返回后 `actions.ts:105-106` 才 `restoreSidecar()` → `maybeRestoreLastPage()` → `app:recentGet` 读到的已是 **page 1**;
  5. `reading.ts:99` `if (page <= 1 ...) return` → **不跳转**;且因记录已被覆写成 1,下次打开同样失效。
- **后果**:只要文档打开超过 700ms(基本等于所有非小文档),「已回到上次阅读位置」这个**已上线功能对用户静默完全失效**,
  且每次打开都会把记录位置覆写为 1,不可逆。
- **修复**:两种改法任选 —— ①把 `recentSet` 移进身份守卫内,并在 `openByPath` 未完成前**不启动 settle 定时器**
  (例如 docId watcher 里跳过首次,改由「打开流程真正结束」时再 `scheduleSettle()`);②`maybeRestoreLastPage` 在读之前,
  先把 `openByPath` 期间产生的 page-1 写入延后/抑制。

### P1-2 图片转 PDF 超 200 张:主进程 throw,渲染层无提示,表现为「点了没反应」
- **位置**:`src/main/ipc.ts:608`(缺 `guard()`)、`src/main/lib/imagetopdf.ts:48`(throw)、`src/renderer/src/components/ImageToPdfDialog.vue:30`
- **已核实**:该 handler 是少数没被 `guard()`(`ipc.ts:86`)包的入口;异常穿透到渲染层变未处理 rejection。
  `runBusy`/`finally` 会复位(不会卡 loading),但对话框无任何提示,用户反复点反复无反应。
  对话框 `canStart` 只校验 `>0`,**不校验上限**,可无限追加到 201 张。
- **修复**:`img:toPdf` 用 `guard()` 包住;`imagesToPdf` 两个校验改为返回 `{ok:false,error}` 而非 throw;
  对话框加 200 张上限提示;渲染层补 catch → `showToast`。

### P1-3 导出/拆分/存图 4 处直写覆盖目标文件,中途失败摧毁原文件
- **位置**:`src/main/lib/docops.ts:186,324`、`src/main/ipc.ts:637,657,668,694`
- **已核实(模式不一致)**:`save` 路径(`ipc.ts:407-432`)正确用 `tmpPath + rename` 原子写;
  上述 4 处却是裸 `writeFile(target)`,以 `'w'` 打开**先截断再写**,磁盘满/被杀/杀软锁文件 → 原文件不可恢复损坏。
  这是**遗漏而非设计取舍**(同文件两种标准)。
- **修复**:抽公共 `atomicWrite(target,data)`(tmp→rename,Windows rename 覆盖),替换这 4 处 + `app:saveImages`。

### 回归 3 —— step8「保存成功」`Can't embed page with missing Contents`(**根因是本轮 P0-2 自己引入的**)

这轮曾一度被误判为「既有缺陷」,基线对照推翻了该判断 —— 基线是全绿的。真实链条:

1. P0-2 给 `readImageBuffer` 加了「必须是用户导入过的路径」授权校验;
2. 图片批注保存时 `resolveImage` 先查内存缓存(未命中)→ 退回 `readImageBuffer(ann.refPath)`;
3. 该 `refPath` 从未经 `importImage` 导入 → **返回 undefined** → 图片画不出来;
4. 但 `buildAppearance` 已经建好 scratch 页 → 页面没有 `/Contents` →
   `embedPage` 在 `save()` 里抛 `Can't embed page with missing Contents`,**整次保存失败**。

项目本就有针对该报错的绕过(`hasDrawableAppearance`,只挡「空文本注释」),P0-2 让它第一次被真正触发。

**修法(两层)**:
- **读到即授权**:`img:getByPath` 成功读取后登记该路径 —— 图片既然已经显示过一次,保存阶段就该能用同一 `refPath` 取回它;
- **真正的兜底**:`buildAppearance` 在 embed 前检查 `scratch.node.Contents()`,没有就放弃该批注的外观并返回 `null`。
  批注对象仍写入产物,其它阅读器照样画默认外观,而**一条有问题的批注不会再炸掉整次保存**。
